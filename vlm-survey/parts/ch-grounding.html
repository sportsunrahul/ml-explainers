Say where, not just what

Every model so far answers in words: it can say "a dog", but not which pixels are the dog. The fix in this chapter is almost embarrassingly simple: a box is four numbers, numbers can be written as text, and a language model already knows how to write text.

The wall: an answer with no address

Ask a LLaVA-style model "where is the ball?" and the best it can do is "at the bottom, next to the dog". That is fine for chat, but useless for a robot arm, a document parser that must say which box on a form holds the date, or a checker that wants to verify an answer against the image. Classic detectors do give coordinates, but through a separate head with its own loss, one head per task. The question this chapter answers: can the language model's ordinary next-token output carry a location?

A box is four numbers, and numbers are text

Qwen-VL's answer (the same model whose resolution work was the previous chapter) is to just write them. Each box coordinate is normalised to the range [0, 1000) and written in the string form (X_topleft,Y_topleft),(X_bottomright,Y_bottomright), between <box> and </box>. The phrase the box belongs to goes between <ref> and </ref>. A real training example from the paper's appendix reads <ref>the ear on a giraffe</ref><box>(176,106),(232,160)</box>. The digits are tokenised as ordinary text; the coordinates need no new vocabulary (only the markers <box>, </box>, <ref> and </ref> are added). Press Box the dog and read the first line: the model's answer is a short sentence of digits and brackets.

Why normalise? Because images come in every size and the model never sees them at that size (Qwen-VL resizes every image to 448 × 448), so a box in the original image's pixels would not match what the model sees. Dividing by the width and height turns "pixel 137 of 640" into "21.4% of the way across" (Qwen-VL writes 214), which means the same thing whatever the resolution; the thousandfold scale just makes it an integer. Trained on grounding data in this form, Qwen-VL reaches 89.36 / 92.26 / 85.34 on RefCOCO val / testA / testB, the task of boxing the object a sentence describes.

How precise is a token?

Writing a coordinate as an integer out of a thousand throws information away: every position inside one thousandth of the image is written the same way. How much does that cost? Drag the bins slider down, or press Coarse: 8 bins. The brown grid is the set of cells the image is now divided into; the yellow box can sit anywhere, but its written form can only name a cell, and the red dashed box, decoded back from the tokens, snaps to cell centres. With B bins across an image of width W, the worst error is half a cell:

k = \Big\lfloor \frac{x}{W}\,B \Big\rfloor, \qquad \hat x = \Big(k + \tfrac12\Big)\frac{W}{B}, \qquad |x - \hat x| \le \frac{W}{2B}.

Not from any of the papers: the bin rule written out; numbering bins from zero and decoding at the centre are the toy's conventions.

At 8 bins on the toy's 640-pixel width that is 40 px, a box that visibly misses the dog. At 1,000 bins it is 0.32 px, and even on a 3840-pixel-wide 4K frame only 1.92 px. None of the papers says why it chose about a thousand levels per axis, but the numbers make it a comfortable choice: fine enough to be invisible and, for Florence-2's one token per level, a small addition to the vocabulary.

Florence-2: every vision task is a sentence

Microsoft's Florence-2 takes the idea to its end. Instead of digits, it creates 1,000 bins and adds one new location token per bin to the tokenizer's vocabulary. The main text never spells a token out, but the appendix prompts (Fig. 16) print them as <loc_586> (angle brackets and an underscore), so that is the form the second line uses. A box is four location tokens (top-left corner, then bottom-right); a text region is a quadrilateral of eight, corners clockwise from the top-left; a segmentation mask is a polygon of 2n tokens for n vertices, also clockwise. Press Box the sign: with the slider at 1,000 the integers on the first two lines are identical, and only the spelling differs. Qwen-VL writes the number with digit tokens the model already had; Florence-2 gives each bin its own token.

With coordinates as tokens, every task becomes the same task. Captioning is "image + caption prompt → text". Detection is "image + prompt → each object's label with its four location tokens". Grounding, OCR with regions and referring segmentation are the same with quads or polygons. There are no task-specific heads, and one loss trains all of them, the ordinary language-model loss over the target tokens:

The architecture is deliberately plain: a DaViT image encoder turns the image into visual tokens, a linear layer and layer norm map them to the text width, and a standard transformer encoder-decoder reads [visual tokens, prompt] and writes the answer. The models are small, 0.23B and 0.77B parameters.

What makes it work is data. A single model doing a dozen tasks needs every image labelled for every task, and no such dataset existed, so the authors built one: FLD-5B, with 5.4B annotations on 126M images (500M text annotations, 1.3B region-text pairs and 3.6B text-phrase-region triples). Almost none of those labels were drawn by hand for FLD-5B (human boxes that came with a source dataset, such as Objects365, were merged in). A data engine made the rest in three phases: (1) initial annotation with specialist models, (2) data filtering, (3) iterative data refinement. In phase 3 a Florence-2-style model trained on the filtered labels re-annotates the same images, its output is merged back in, and the loop repeats: the same "let the model clean its own data" move as BLIP's CapFilt in Act II, now for boxes and masks. Fine-tuned as one generalist, Florence-2-B / -L reach 92.6 / 93.4 on RefCOCO val.

Molmo: point, then count

A box takes four numbers and a careful annotator. Molmo (from the Allen Institute for AI) asks for less: a single point, which a person can click in a second. Its model writes points as plain-text coordinates normalized between 0 and 100, with one decimal, inside an HTML-like tag: <point x="10.0" y="10.0" alt="...">text</point>. Drag the yellow dot and watch the third line. One decimal on a 0-100 scale is again a thousand steps per axis, the same precision as the other two.

Points pay off in an unexpected place: counting. Press Point, then count. Instead of blurting "3", Molmo first writes one numbered point per apple, in a fixed order (top to bottom, then left to right), and the count is just the last index it wrote. It is chain-of-thought, but the "thoughts" are locations you can check against the image. Molmo's ablation shows the order matters: point-then-count scores 89.4/86.3 (CountBenchQA / PixMo-Count), against 87.9/80.2 for answering with the count alone, and 81.5/77.6 for giving the count first and pointing afterwards.

Now predict before you press. Florence-2 adds special location tokens (an idea it credits to earlier sequence models such as Pix2Seq, Unified-IO and OFA); Qwen-VL and Molmo write plain digits. Molmo tested exactly this, on its own pointing data at equal precision: 1000 special point tokens added to the vocabulary, against coordinates written in digits. Which works better? Press Molmo's answer. Plain digits win on both benchmarks, 89.4/86.3 against 85.8/80.9. A plausible reading, not one the paper tests: a thousand fresh tokens start with random embeddings and must each be learned from the grounding data alone, while digits arrive already ordered (the model knows 41 is next to 42) from all of its text pretraining. Keep the scope in mind, too: this is one ablation, on points and counting in one model family, not a verdict on Florence-2's boxes.

Look back at what this chapter did: a choice (digits or new tokens), a knob (how many bins), and one small experiment that settled the choice for one setting. Most of the choices in the earlier chapters (which language model, which encoder, which connector, how many image tokens, whose captions) never got even that.
