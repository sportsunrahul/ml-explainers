Act IVSeeing sharply and pointing

A fixed small square cannot read a page

Every model so far squeezes each picture into one small square before its encoder sees it: CLIP's ViT-L/14 encoder comes in 224 vs 336 pixel versions, LLaVA-1.5 uses 336 and Qwen-VL 448. That is plenty for a photo of a dog and hopeless for a page of text, where the letters shrink to a pixel or two.

The wall: shrinking the page

Start where the last act left off. LLaVA-1.5 feeds its language model a 336-pixel square, chosen because it is the highest resolution available for CLIP, and that square becomes 576 tokens. The figure opens there, on a report page. Its body text is set in 16-pixel type; squashed into 336 × 336 it arrives 3.8 pixels tall, and the zoom panel shows what that means: grey smudges where words used to be. Press 224 square and it is worse (2.6 pixels). Try the wide screenshot too: a square also throws away the aspect ratio, so the code is squeezed 1.8 times harder across than down.

Qwen-VL's first move was the obvious one. Its authors increase the input resolution of the visual encoder from 224 x 224 to 448 x 448, reducing the information loss caused by image down-sampling. Doubling the side quadruples the patches: the encoder (initialized from OpenCLIP ViT-bigG) now runs at 448x448, ViT sequence length 1024. To keep the language model's share small, Qwen-VL adds an adapter in the spirit of BLIP-2's query tokens: a single-layer cross-attention module initialized randomly, whose 256 learned queries read the patch features and compresses the visual feature sequence to a fixed length of 256. Because compression scrambles where things were, 2D absolute positional encodings are added inside that cross-attention. Press 448 square (Qwen-VL): the type now arrives 5.1 pixels tall, better but still blurry, for about the same number of tokens as the 224 square: 258 against 256, because Qwen-VL brackets its 256 outputs with the two markers <img> and </img>.

Training runs in three stages, much like the recipes of the previous chapter: first at 224x224, ViT sequence length 256 with the language model frozen, then at 448 with nothing frozen on a multi-task mix, then instruction tuning for chat with the ViT frozen. On DocVQA, a benchmark of questions about scanned documents, Qwen-VL scored 65.1. A bigger square helps, but any fixed square is too small for some image and too big for another.

Tiling: more squares

A common fix, used in different forms by LLaVA-1.5-HD, Idefics2 and Molmo, keeps the encoder at its native size and gives it more squares. LLaVA-1.5-HD describes it as dividing the image into smaller image patches of the resolution that the vision encoder is originally trained for, encoding each crop separately and stitching the features back into one large map. Seen crop by crop, the model loses the big picture, so a shrunken copy of the whole image comes along to provide the LLM with the global context and to reduce the artifact of the split-encode-merge operation. Idefics2 turns each image into 4 crops and the original image, at a cost in visual tokens per image of 64 / 320 without and with splitting. In Molmo, the grid is chosen to require the least amount of up-scaling, and neighboring crops overlap so that patches at a seam still see their neighbors.

Press Tiles + thumbnail on the document page. The toy picks a 2 × 3 grid of 224-pixel crops, and the type now arrives 7.2 pixels tall: most words are legible in the zoom. The bill is 1,774 tokens (the grid's patches, one row-end token per row, and the thumbnail's 256). Tiling works, but it is a patch on a fixed-size encoder: the crops come in a few fixed shapes, the image still gets resized to fit them, and because the crop count is capped, a big screenshot is still shrunk to about a third of its width (switch to it: the code arrives 5.3 pixels tall).

Native resolution: let the image keep its size

Qwen2-VL removes the square altogether. The model can process images of any resolution, dynamically converting them into a variable number of visual tokens, using two changes to the recipe of chapter 3.

First, the ViT's position table goes. A learned table has one row per slot and must be interpolated for every new grid size; Qwen2-VL modified the ViT by removing the original absolute position embeddings and introducing 2D-RoPE, a rotary position code computed from each patch's row and column, so any grid size works without a table. Second, to pay for the extra patches, a small MLP after the ViT is used to compress adjacent 2x2 tokens into a single token. With the ViT's patch_size=14, one language-model token now stands for a 28 × 28 = 784-pixel square of the image. The paper's own example: a 224x224 image will be compressed to 66 tokens, which is 16 × 16 = 256 patches, merged four to one into 64, plus two marker tokens around them. As a formula:

T = \htmlData{step=1, link=patch}{\frac{\htmlClass{t-blue}{H'}}{14}\cdot\frac{\htmlClass{t-blue}{W'}}{14}} \;\htmlData{step=2, link=merge}{\cdot\;\frac{1}{2 \times 2}} \;\htmlData{step=3, link=special}{+\;\htmlClass{t-yellow}{2}} \qquad \htmlData{step=4, link=size}{\htmlClass{t-blue}{H'} \approx H,\;\; \htmlClass{t-blue}{W'} \approx W}

Not numbered in the paper; written out from Qwen2-VL v2, Sec. 2.1 (the 224 × 224 → 66 tokens example).

  • \htmlClass{t-blue}{H'}, \htmlClass{t-blue}{W'}: the image's own height and width, changed only slightly so the grids come out even. The paper does not say how it rounds; the figure snaps each side to the nearest multiple of 28.
  • \tfrac{H'}{14}\cdot\tfrac{W'}{14}: the number of 14-pixel patches, each one token inside the ViT (the fine grid in the figure).
  • \tfrac{1}{2 \times 2}: the MLP merge, four neighboring patch tokens into one (the heavier grid, one cell per language-model token).
  • \htmlClass{t-yellow}{+\,2}: the <|vision_start|> and <|vision_end|> markers placed before and after the image's tokens (yellow in the figure's "LLM reads" row, because they are ordinary vocabulary tokens).
  • T: the number of tokens the language model reads for this image. It grows with the image's area, as in chapter 3, but now at one token per 784 pixels instead of one per 14-pixel patch (196 pixels).

Now check your prediction. Press Small photo, then Native size (Qwen2-VL). The 400 × 300 photo costs 156 tokens, fewer than the 448 square's 258, and its encoder does less work too: 616 patches instead of 1,024, because the square had to blow the photo up before cutting it. A fixed size is wrong in both directions: it blurs big images and wastes tokens on small ones. Switch to the document page and native size reads the page at full sharpness (1,752 tokens); the wide screenshot costs 2,693. To keep extremes in check, the paper's resolution ablation sets min_pixels=100x28x28, max_pixels=16384x28x28, that is, between 100 and 16,384 tokens per image; those are the ablation's settings, not stated as defaults. Images of different sizes then simply make sequences of different lengths, and at inference images of varying resolutions are packed into a single sequence, the packing trick of the previous chapter.

Does it pay? The paper compares Qwen2-VL-7B fed a fixed number of tokens per image, resized rather than resizing to a specific height and width, as this would distort the original aspect ratio, against dynamic resolution. At fixed budgets of 64 / 576 / 1600 / 3136 tokens, InfoVQA (questions about infographics) scores 28.85 / 65.72 / 74.99 / 77.27 vs 75.89 for dynamic resolution, which used 1924 tokens on average; on OCRBench the fixed budgets score 572 / 828 / 824 / 786 vs 866. So dynamic resolution comes within about a point and a half of the biggest fixed budget on InfoVQA with fewer tokens, and beats every fixed budget on OCRBench. The headline is DocVQA, the same benchmark as before: Qwen2-VL scores 96.5 / 94.5 / 90.1 (72B / 7B / 2B models), against Qwen-VL's 65.1. All three sizes share one 675M-parameter ViT, paired with language models of 1.5B / 7.6B / 72B parameters.

Positions in two dimensions, and in time: M-RoPE

The language model has the same kind of position problem the ViT had. With ordinary 1D RoPE every token gets the next integer, so the document page above at native size, a 35 × 50 grid of image tokens, is just 1,750 consecutive positions: the token directly below another sits 35 positions away, and a big image pushes the text after it far down the number line. Qwen2-VL's Multimodal Rotary Position Embedding (M-RoPE) splits the rotary embedding into temporal, height, and width parts, so each token carries three ids (t, h, w).

The rule has three parts. For text, the three components utilize identical position IDs, so a text-only prompt is numbered exactly as under 1D RoPE and the language model's reading of text is untouched. For an image, t stays constant across all its tokens, while h and w are the token's row and column. For a video, t goes up by one per frame. And across modalities, position numbering for each modality is initialized by incrementing the maximum position ID of the preceding modality by one. The paper's figure makes "maximum" concrete: after a video of three frames, each 3 × 4 tokens, numbered from 0, the text continues at (4,4,4), then (5,5,5), (6,6,6). The largest component in the block was a width id of 3, so text resumes at 4.

\begin{aligned} &\htmlData{step=1, link=text}{\htmlClass{t-yellow}{\text{text token } n}:\quad (n,\; n,\; n)} \\ &\htmlData{step=2, link=img}{\htmlClass{t-blue}{\text{image token at row } r,\ \text{column } c}:\quad (s,\; s + r,\; s + c)} \\ &\htmlData{step=3, link=video}{\htmlClass{t-blue}{\text{video token in frame } f}:\quad (s + f,\; s + r,\; s + c)} \\ &\htmlData{step=4, link=next}{\text{next block starts at } \max(t, h, w) + 1} \end{aligned}

Not an equation in the paper: the rule stated in Qwen2-VL v2, Sec. 2.1, and drawn in its M-RoPE figure.

  • (t, h, w): the three ids. The rotary embedding's dimensions are split into three groups, and each group is rotated by one of the three ids instead of all by the same one.
  • n: a text token's ordinary running position, used for all three parts.
  • s: the first id of a visual block, one past the largest id before it. The tokens are the merged 28-pixel tokens, rows and columns counted from 0.
  • f: the frame number within a video.
  • \max(t, h, w) + 1: where the next block, text or visual, starts: one past the largest id used anywhere in the block, which is the block's start plus its longest side.

So check the prediction: the image starts at 3, its largest id is a width of 3 + 3 = 6, and "The" gets 7 under M-RoPE, not 15. The bar under the tokens shows the whole budget: under 1D RoPE the sequence uses ids 0 to 18, under M-RoPE only 0 to 10, because a visual block uses only as many ids as its longest side. Press Add a short video and the gap widens: 35 versus 18. The same holds for real videos, which Qwen2-VL samples at two frames per second and encodes with a 3D convolution of depth two, so that pairs of frames become one slice of tokens (for consistency each image is treated as two identical frames).

Small position ids are the point: the paper credits M-RoPE with letting the model run on longer inputs than it was trained on. Trained with at most 16384 tokens per video, it keeps working on video inputs up to 80K tokens. In the paper's ablation (a smaller model, 1D RoPE vs M-RoPE), the switch moves image scores such as MathVista 39.2 vs 43.4; MMB 58.6 vs 60.6 and video scores such as NextQA 43.9 vs 46.0; STAR 55.5 vs 57.9; several document benchmarks in the same table barely move.

Inside Qwen2-VL: forward, then backward

Now put the two changes back into the whole model and follow one training example through it. The line under the drawing gives the tensor shape at each stage, computed from the patch size, the merge and the paper's own example images; switch the input to watch the token count follow the image, and switch the training stage (Qwen2-VL's three, or Qwen-VL's three for comparison) to see which boxes learn.

Answer to the prediction: yes. Freezing a box stops its update, not the gradient; anything upstream of a frozen language model still learns through it, which is exactly what Qwen2-VL's first stage relies on. Put the two models side by side on the web page and the difference in cost is stark: Qwen-VL hands the language model 258 tokens for it at any stage, Qwen2-VL 11,429, about 44 times more, which is why its resolution ablation caps an image at min_pixels=100x28x28, max_pixels=16384x28x28 (video has its own, separate cap of 16384 tokens per video in training) and why the next generations work so hard on what those tokens carry.

A model that reads the page at its own resolution, with image tokens that know their row and column, can do more than read: it can say where. The next chapter shows how "where" becomes just more tokens, written as coordinates in the output sequence, as plain digits or as dedicated location tokens.
