The parallel scan and the hardware-aware kernel

Selection took away S4's shortcut. When \overline{A} and \overline{B} change at every token there is no single kernel to convolve with, so the states must come from the recurrence itself, and a loop over L tokens takes L steps, one after another: exactly what made RNNs slow to train. But each step is still linear in \htmlClass{t-yellow}{h}, and that is enough to compute all L states in about 2 \log_2 L rounds instead.

Step through it with Next level. Write one step of the recurrence, \htmlClass{t-yellow}{h_t} = a_t \htmlClass{t-yellow}{h_{t-1}} + b_t, as the pair (a_t, b_t): keep a_t of the old state, then add b_t. In Mamba, a_t = \overline{A}_t and b_t = \overline{B}_t \htmlClass{t-blue}{x_t}, separately for each state cell. Two steps in a row are again one step of the same form, so two pairs can be merged into one before anyone knows what state they will be applied to. In the up-sweep, neighbours merge in parallel: pairs of tokens, then fours, then eights, until the root holds the effect of the whole sequence. In the down-sweep, each node is handed the state just before its span: a left child copies its parent's, and a right child merges its parent's with its left sibling's pair. One last merge per token turns "the state before me" into "my state".

Martin and Cundy, who parallelized linear RNNs this way in 2018, write a step as an operator (\Lambda, x) \bullet h = \Lambda h + x. The merge rule below is our derivation from it: apply one step, then the next.

\begin{aligned} &\htmlData{step=1, link=pair}{\htmlClass{t-yellow}{h_t} = a_t\, \htmlClass{t-yellow}{h_{t-1}} + b_t \quad\longleftrightarrow\quad (a_t,\ b_t)} \\[4pt] &\htmlData{step=2, link=combine}{(a_1, b_1) \circ (a_2, b_2) = (a_1 a_2,\ \ a_2 b_1 + b_2)} \\[4pt] &\htmlData{step=3, link=assoc}{(p \circ q) \circ r = p \circ (q \circ r)} \\[4pt] &\htmlData{step=4, link=state}{\htmlClass{t-yellow}{h_t} = \text{the } b \text{ of } (a_1, b_1) \circ (a_2, b_2) \circ \cdots \circ (a_t, b_t), \quad \htmlClass{t-yellow}{h_0} = 0} \end{aligned}

Line 1 is Martin and Cundy's operator (Algorithm 1, line 2) in this page's letters. Lines 2 to 4 are our derivation from it. Mamba cites the parallel scan (Blelloch; Martin and Cundy; S5) and calls its own computation "recurrence (scan) only" (Algorithm 2, line 6), without writing the operator.

  • a_t is how much of the old state survives step t (a decay between 0 and 1 in Mamba), and b_t is what step t writes. The pair is the whole effect of one step on any state.
  • \circ means "apply the left pair, then the right one". The result is one pair that does both steps. Order matters: swap the two and you get (a_1 a_2,\ a_1 b_2 + b_1), a different step.
  • Grouping does not matter (associativity, which you can check by expanding both sides). So any tree of merges gives the same answer, and a parallel machine is free to pick the shallowest tree.
  • Starting from \htmlClass{t-yellow}{h_0} = 0, the merged pair for tokens 1 to t maps 0 to its own b, which is therefore \htmlClass{t-yellow}{h_t}.

Before you press All states: will the scan do less arithmetic than the loop, or more? It does more. For 8 tokens the tree needs 22 combines against the loop's 8 steps, about three times the work, but in 7 rounds that each run in parallel. The rounds grow with \log_2 L, so the gap opens quickly: at 2,048 tokens the scan needs 23 rounds instead of 2,048. Martin and Cundy count the same trade for p processors: O(6n(T/p + \lg p)) for the parallel scan against O(2nT) for the serial one, with n features and T steps.

Against attention, the training bill now reads: attention scores about L^2/2 pairs per head per layer, while the scan does about 3L combines per state cell, in about 2\log_2 L rounds.

Where the state lives

The tree fixes the depth. It does not fix the size. Every token's state has D \times N numbers, so the states of a whole batch form a tensor of shape (B, L, D, N), N times larger than the layer's input and output of shape (B, L, D). On a GPU, most operations other than matrix multiplication are limited by how fast data moves to and from memory, not by arithmetic (Mamba, Sec 3.3.2), so writing that tensor out and reading it back would cost more than computing it.

Mamba's kernel answers with three classical techniques, all named in its Sec 3.3.2. Kernel fusion: discretization, the scan and the multiplication by C run inside one GPU kernel, so the (B, L, D, N) values exist only in SRAM, the small fast memory on the chip, and only the inputs and the output cross to HBM, the large slow memory. The parallel scan runs inside that kernel. Recomputation: the states are not saved for the backward pass but recomputed when the inputs are loaded again, which is cheaper than storing them and reading them back. A sequence too long for SRAM is cut into chunks, and the scan carries its state from one chunk to the next (App. D). In the figure the fused kernel moves about 33 times fewer bytes than the standard route; Mamba states the saving as a factor of order N in memory traffic.

Claim card: the fused scan is fast, and costs about as much memory as FlashAttention

Claim
The hardware-aware scan is much faster than a standard scan, faster than the best attention kernel on long sequences, and needs about the training memory of a well-optimized Transformer.
How it was measured
On an A100 80GB PCIe: the scan alone at batch 1, 1024 channels, state size 16, lengths up to 500K, against a PyTorch scan without fusion, a PyTorch FFT convolution and FlashAttention-2. Memory: training 125M-parameter models on sequences of 2048 tokens, against a Transformer with FlashAttention-2 and torch.compile fusion.
Result
Speed: "up to 20-40x faster than a standard scan implementation in PyTorch" (Sec 4.5; App. D says the same); the caption of Fig. 8 rounds it to 40x. Faster than FlashAttention-2 beyond 2K tokens, and up to 7x faster than attention at 32K (App. D). Memory (Table 15):

What would have falsified it
Memory growing with the state size N, as it must if the (B, L, D, N) states were stored for the backward pass. It stays within about a tenth of the Transformer's.

When the tree does not pay

The tree buys depth with extra work, so it wins only when there is enough length to spread. Martin and Cundy's parallel kernel runs at 0.06 times the speed of a serial one on 16-step sequences, and 38.5 times faster on 65,536 steps (their Table 1, 4 features). Hardware matters as much. Griffin, trained on TPU-v3, found the associative scan "significantly slower" than a plain sequential scan: its training step was up to 50% slower with it. Its authors wrote a sequential scan kernel that keeps the state in fast on-chip memory, almost 3x faster than the default JAX version, and guess that the tree's scattered memory access suits the TPU poorly. Our reading: the two papers agree on what matters, keeping the state in fast memory and moving as few bytes as possible; they differ on whether the tree is worth its extra work on their hardware.

None of this runs when the model writes text. Generating one token at a time, a selective SSM takes exactly one step of its recurrence per token and keeps one state, which is where the flat yellow line of the first chapter comes from. The interlude follows one such token through a whole model, next to a Transformer reading its cache. After it, Mamba-2 finds a third way to compute the same states, one that runs on the GPU's matrix-multiply units.
