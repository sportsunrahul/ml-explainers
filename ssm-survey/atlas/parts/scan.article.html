The parallel scan

All the states of a recurrence, in a few rounds instead of one per token

Tokens
Step

Selection makes the recurrence change at every token, so the convolution trick of S4 is gone. A plain loop computes the states one after another: L tokens, L steps in a row. But every step is still "keep a of the old state, add b", and two such steps merge into one: (a1, b1) then (a2, b2) is (a1 a2, a2 b1 + b2). That merge is an , so the states can be computed as a , on a tree.

Going up, neighbours merge in parallel until the root holds the whole sequence. Going down, each node receives the state just before its span (yellow). One last merge per token gives every state. For 16 tokens: 9 rounds instead of 16, for about three times the arithmetic. At 2,048 tokens: 23 rounds instead of 2,048.

Kernel
Stage

Each token's state has D x N numbers, N = 16 times more than the layer's input and output. Writing all of it to the GPU's main memory and reading it back would cost more than computing it, because moving bytes, not arithmetic, is the bottleneck (see ).

Mamba uses : the expanded state lives only in fast on-chip memory, one chunk at a time, and only inputs and outputs travel. For the backward pass it uses instead of storing the states. In our count for one layer of Mamba 2.8B at 2,048 tokens, that is about 33 times less memory traffic.

The tree is a toy with exact arithmetic: one state cell, random decays, checked against the plain loop. The memory picture is computed: one layer, 2,048 tokens, inner width 5,120, state size 16, 16-bit values; the bytes per stage are our count of the reads and writes Mamba's appendix describes.

The tree is not always worth it: on 16-step sequences Martin and Cundy's parallel kernel ran at 0.06 times the serial speed, and Griffin found the tree slower than a sequential scan on TPU-v3.

A linear recurrence can be computed like a sum: in log-depth rounds on a tree, with the big state kept in fast memory and never written out.
